# 08 — Добавление сотрудников по номеру телефона

## Итог

Во всех внешних формах добавления людей используется номер телефона. Внутренний
идентификатор пользователя frontend не запрашивает, не хранит и не отправляет.

Поддерживаются четыре сценария:

| Кто создаёт | Кого создаёт | Endpoint | Тело |
|---|---|---|---|
| Супер-админ или администратор магазина | Администратора или сотрудника | `POST /admin/v1/merchants/{merchantId}/members` | `{ fullName, phone, role, branchId? }` |
| Супер-админ | Администратора филиала | `POST /admin/v1/merchants/{merchantId}/members/partners` | `{ fullName, phone, scanOperation, branchId? }` |
| Администратор филиала | Сотрудника с унаследованным правом | `POST /admin/v1/members/{partnerMemberId}/employees` | `{ fullName, phone }` |
| Администратор филиала | Web-кассира | `POST /admin/v1/members/{partnerMemberId}/cashiers` | `{ fullName, phone }` |

`phone` принимается в международном формате, например `+996700123456`. Сервер хранит
нормализованное значение `996700123456`. Номер без кода страны отвечает `400`.

## Регистрация предсозданного человека

Создание сотрудника резервирует телефон и создаёт аккаунт со статусом
`registrationStatus: "pending"`. Это не считается завершённой регистрацией и не должно
показываться человеку как ошибка «номер уже зарегистрирован».

Человек запрашивает OTP и вызывает обычный endpoint:

```http
POST /auth/register
{ "phone": "+996700123456", "otp": "123456", "deviceId": "persistent-device-id" }
```

Также допустим `POST /auth/login` с теми же полями. Оба адреса выполняют единый
sign-in-or-sign-up flow. Первый успешный OTP-вход активирует существующую запись и сразу
выдаёт JWT с назначенными магазином, филиалом и ролью.

Ответ первой регистрации предсозданного аккаунта:

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "expiresIn": "12h",
  "refreshExpiresIn": "30d",
  "isNewAccount": true,
  "registrationCompleted": true,
  "message": "Сотрудник зарегистрировался"
}
```

В зависимости от роли `message` содержит:

- `Администратор филиала зарегистрировался`;
- `Сотрудник зарегистрировался`;
- `Кассир зарегистрировался`.

После входа списки сотрудников и кассиров возвращают
`registrationStatus: "registered"` и ISO-дату `registeredAt`. Web сравнивает прошлое
значение `pending` с новым `registered` и показывает сообщение снизу экрана.

## Ответ создания

```json
{
  "id": "membership-uuid",
  "merchantId": "merchant-uuid",
  "userId": "server-only-reference",
  "role": "staff",
  "branchId": "branch-uuid",
  "fullName": "Айжан К.",
  "phone": "996700123456",
  "registrationStatus": "pending",
  "registeredAt": null,
  "message": "Сотрудник добавлен"
}
```

`userId` может присутствовать в ответе как серверная ссылка, но нигде не используется
для добавления. Во всех `POST` выше поле `userId` является лишним и отвечает `400`.

## Журнал списаний

`GET /admin/v1/merchants/{merchantId}/deductions` возвращает в каждой строке
`cashierName`. Для списаний из web/scanner это имя профиля человека, выполнившего
операцию. Для старых записей и операций 1С без конкретного кассира приходит `null`;
frontend показывает `—`.

## Проверочный сценарий

1. Создать сотрудника новым номером — получить `pending`.
2. Убедиться, что повторное добавление в тот же магазин отвечает `409`.
3. Зарегистрировать номер по OTP — получить токены и `registrationCompleted: true`.
4. Перечитать список — статус `registered`, `registeredAt` заполнен.
5. Убедиться, что JWT содержит назначенное членство и филиал.
6. Создать кассира по номеру, войти по OTP и выполнить списание.
7. Проверить собственную историю кассира и `cashierName` в общем журнале.
8. Отправить вместо телефона `{ userId, role }` — получить `400`.

## Безопасность

- Клиент не назначает себе роль или филиал при OTP-регистрации: они уже определены
  создавшим администратором.
- Филиал проверяется на принадлежность магазину.
- Нельзя привязать удалённый, служебный или супер-административный аккаунт.
- Удаление кассира отзывает его активную сессию.
- Закрытая связь auth-service с core-service использует внутренний ID только после
  серверной проверки invite-кода; этот маршрут не проходит через gateway и не является
  frontend API.
