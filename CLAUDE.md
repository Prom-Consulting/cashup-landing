# Loal — правила архитектуры

Монорепо pnpm: `apps/landing` (loal.kg), `apps/admin` (admin.loal.kg), `apps/partner`
(partner.loal.kg), `apps/client` (client.loal.kg), `apps/cashier` (cashier.loal.kg). Общее — в `packages/`. Подробности и команды —
README.md. Бэкенд живёт в соседнем репозитории `cashup_platform`, шлюз — `loal.promconsult.pro`.

## Лендинг — SEO прежде всего

Страницы статические (SSG) или серверные; текст должен попадать в HTML без JavaScript.
`"use client"` — только для интерактивных островков (анимации, калькулятор, карта, формы).
У каждой новой страницы — `metadata` с title, description, canonical и Open Graph, и строка в
`app/sitemap.ts`. Сборка должна показывать страницы как `○ (Static)` (или `● (SSG)` у страниц с `generateStaticParams`).

Title и description — только из `app/_data/seo.ts` (образец — `docs/SEO`): своя пара у каждой страницы, шаблоны у
однотипных, description до 160 знаков. Каталог: `/partners` — витрина (карта — `?view=map`), `/partners/{категория}` —
страница категории (пустая — `noindex` и не в sitemap), `/partners/{категория}/{название-латиницей}-{8 знаков id}` —
страница заведения с LocalBusiness и хлебными крошками; заведение ищется по коду, старый адрес отдаёт 308 на новый.
В шапке на страницах для бизнеса (`audience="business"`) вместо «Моя карта» — «Мой бизнес» на partner.loal.kg.

## Кабинеты — чистый CSR и FSD

Vite SPA, без SSR, закрыты от индексации (`noindex` в index.html, robots.txt, заголовок в
`infra/nginx/spa.conf`). В sitemap лендинга их не добавлять.

Слои Feature-Sliced Design, импорт разрешён только вниз:

```
app → pages → widgets → features → entities → shared
```

- слой не импортирует сам себя через соседний срез: общее поднимается на слой ниже или в пакет;
- запросы к API живут в `entities/<домен>/api.ts` рядом с ключами кэша, экраны их только вызывают;
- действия пользователя (вход, смена статуса, добавление сотрудника) — `features/`, а не в странице;
- новый общий для кабинетов кусок — сразу в `packages/` (`@loal/ui`, `@loal/app-kit`), не копией.

## Контракт с бэкендом

`docs/API.md` — справочник шлюза, его обновляют в том же коммите, что и само API. Это источник
правды: схемы в `@loal/api` следуют ему, а не тому, что удалось вычитать в коде бэкенда. Если экран
падает на разборе ответа, сначала сверяемся с этим файлом.

Модель после 23 сентября 2026: **карта, клиент, шаблон и программа принадлежат платформе**,
а заведение (`merchant`, бывший `store`) владеет только своими сотрудниками, подпиской, журналом
списаний, витриной и обменом с 1С.

Что из него важно помнить:

- платформенные адреса без заведения в пути (`/admin/v1/customers`, `/admin/v1/cards`,
  `/admin/v1/templates`, `/admin/v1/loyalty-programs`) открыты только агентству — заведению `403`;
- всё про заведение живёт под `/admin/v1/merchants/{merchantId}/...`;
- в токене членства лежат в `merchants[]`, внутри — `merchantId`; старые токены не подойдут;
- у держателя карты есть свой кабинет: `/v1/me/card` и `/v1/me/history` читают человека из
  токена, идентификатора в адресе нет; `404` на карте значит «ещё не выпускали», а не ошибку;
- подписка клиента v2 — цикл 30 дней: цена, срок и баланс только из `GET /v1/me/subscription/offer`,
  оплата `POST /v1/me/subscription/payments { planId }`, возврат с OctōPAY на `/payment/return` и опрос
  до `paid` + `fulfilled`. Оплата ставит баланс ровно в 15 000 (не прибавляет) и сразу начинает новый цикл.
  В конце цикла карта `frozen` (QR и списание — `409 CARD_FROZEN`), через 30 дней остаток сгорает.
  Без карты offer отвечает `intent: "initial"`, и первая оплата сама выпускает карту на телефон аккаунта
  (`400 PHONE_REQUIRED`, если телефона нет). Цена без входа — `GET /v1/public/subscription/offer`.
  Помесячные `{ months }` — только старые админские сценарии и запасной путь, если шлюз отвечает на
  offer `404`;
- витрину (`profile`) PUT заменяет целиком: шлём все шесть полей, пустое — как `null`,
  фотографии — как `[]`; картинки грузятся отдельным запросом до сохранения. `address`, `lat`, `lng`
  необязательны (не прислали — сервер оставит прежние), координаты — только парой; берём их из ссылки
  2ГИС (`coordsFrom2gis`), каталог ставит точку по ним;

- вход отправляет `deviceId` — постоянный, создаётся один раз и живёт в localStorage; у аккаунта
  одна активная сессия;
- если аккаунт открыли на другом устройстве, закрытые запросы отвечают `401` с
  `error: "SESSION_REPLACED"`. Такой ответ нельзя повторять и нельзя молча обновлять сессию:
  чистим токен и показываем сообщение на входе (`ApiError.isSessionReplaced`);
- регистрация сразу выдаёт токен, отдельный вход после неё не нужен; без кода приглашения
  получается сотрудник без доступа к кабинету, с кодом — владелец магазина;
- клиент регистрируется только телефоном и кодом: `POST /auth/register` строгий, лишние поля — 400;
  почта и пароль — только у владельца по приглашению (`register-with-invite`). В токене клиента
  `email: null`. Вход и регистрация клиента — одна форма `PhoneSignInForm` с одним кодом;
- вход возможен и по телефону с кодом из WhatsApp: код живёт 5 минут, на него даётся 5 попыток,
  повтор не чаще раза в минуту (429 с текстом, сколько ждать); код одноразовый — успешный вход или
  регистрация его поглощают;
- у магазина подписка (`isActive`) отвечает за приём бонусов, счета — только за оплату;
- ошибки проверки приходят с массивом `issues` (путь до поля и текст) — он лежит в `ApiError.issues`;
- живые поля карты — по `key` (`balance`, `cardNumber`, `memberName`, `phone`, `memberSince`, `punch`,
  `tier`, `tierReward`, `discount`, `bonusItem`): их `value` сервер подменяет сам. Синтаксиса `{{…}}`
  нет. `dateStyle`/`timeStyle` — только у дат, иначе Apple отвергает карту целиком;
- правка шаблона (`PUT /admin/v1/templates/{id}`) сразу уходит на все выданные карты push-ом,
  отката нет: в редакторе сохранение опубликованной карты идёт только через подтверждение с числом
  держателей; тело — весь `design`, пустые необязательные поля выкидываем (`cleanDesign`);
- потолок процента (`coverage-limit`) заведение меняет раз в месяц (`409` до `nextChangeAt`),
  агентство — когда угодно; касса берёт меньшее из 30% и потолка. Форма общая — `@loal/app-kit`;
- `POST /v1/redemptions` шлёт `merchantId`, только если человек работает в нескольких заведениях:
  с одним местом работы сервер лишнее поле отклоняет;
- пустые необязательные поля уходят на сервер как `null`, а не `""` — строку сервер не пропустит
  (почта заведения, проценты уровня);
- вход по телефону — один код: `/auth/login` с новым номером сам создаёт аккаунт и отвечает
  `isNewAccount: true`; второго кода и `409` больше нет. `503` — хранилище кодов недоступно, это
  «попробуйте через минуту», а не «неверный код»;
- промокоды на бесплатные месяцы — платформенные (`/admin/v1/promo-codes`, только агентству);
  магазин применяет свой через `/admin/v1/merchants/{id}/promo-code` (кассиру `403`), держатель
  карты — через `/v1/me/promo-code` (без карты — `404` «Сначала получите карту»);
- людей заводят заранее по имени и телефону: `POST /admin/v1/merchants/{id}/members { fullName, phone, role, branchIds }`,
  `userId` фронт не шлёт (лишний — `400`); `branch_admin` без филиалов — `400`. Один человек работает в нескольких
  филиалах (`branchIds`, выбор чипами `ChipSelect`), но только в одном магазине: `409 EMPLOYEE_ALREADY_ASSIGNED`.
  Читаем филиалы через `memberBranchIds`/`membershipBranchIds` — у старых ответов только `branchId`. `PATCH { branchIds }`
  заменяет список целиком. Форма общая — `AddMemberForm` (`actor="branch"` — администратор филиалов, только кассиры
  и только в свои филиалы). `409` — номер занят, у поля. До первого входа
  `registrationStatus: "pending"`: списки перечитываются (`refetchWhilePending`), переход в `registered` — `Toast`
  через `useJustRegistered`; первый вход с `registrationCompleted: true` — `WelcomeToast`;
- один телефон — один клиент: `POST /admin/v1/customers` с занятым номером — `409`, показываем у поля;
- баллы переезжают на новую карту человека и с отозванных карт; но новая карта (другой серийный
  номер) в Wallet сама не появляется — клиенту шлют ссылку. Внешний вид меняют правкой шаблона;
- магазин устроен «владелец → филиалы → кассиры». Роли (`merchants[].role`, строкой — старый токен не роняет вход):
  `admin` — владелец (`branchIds: []` — весь магазин), `branch_admin` — администратор филиалов (`merchants[].branchIds`),
  `staff` — кассир. Операция (списание, счёт клиенту) пишется на один филиал: при нескольких фронт шлёт `branchId`
  выбранного (`useWorkBranch` + `WorkBranchPicker`, выбор живёт на устройстве), без него — `400 BRANCH_REQUIRED`;
  у кассира филиалы — `overview.branches`, пустой список — списывать нельзя.
  Кабинет партнёра — владельцу (всё) и администратору филиала: «Команда» (только кассиры своего филиала,
  добавляет только кассиров — филиал ставит сервер), «Списания» (сервер отдаёт его филиал), «Счёт клиенту»;
  разделы владельца закрыты `OwnerOnly` (`allowBranch` — открыть и администратору филиала). Кассира кабинет
  партнёра отправляет на cashier.loal.kg. Роль и филиал в токене обновляются при новом входе, убранного
  человека выкидывает сразу (`401`). Роли «партнёр» и «сотрудник партнёра» удалены вместе с `/admin/v1/members/*`,
  `/admin/v1/partners/*`, бонусом партнёра, `mechanicPartnerAccess`/`bonusItemPartnerAccess` и `?via=`;
- магазин заводит агентство с обязательным телефоном владельца (`contactPhone`): владелец входит обычным OTP, кода
  приглашения не нужно (приглашение — прежний путь). `409 MERCHANT_OWNER_UNAVAILABLE` — номер нельзя сделать владельцем,
  у поля. `DELETE` магазина — архив (`deletedAt`, `?includeDeleted=true`), восстановления нет, правки — `410 MERCHANT_DELETED`;
  агентство смотрит архив только на чтение; через 30 дней после удаления сервер обезличивает магазин (название остаётся);
- выход из программы: магазин себя не удаляет — владелец подаёт заявку (`…/exit-request`, профиль партнёра, кассиру и
  администратору филиала `403`, повторный POST при открытой — та же заявка), агентство решает на экране «Выход партнёров»
  (`/admin/v1/merchant-exit-requests`: approve = удаление, reject — только с причиной). Решение уходит владельцу в WhatsApp;
  `ownerNotified: false` — не дошло, повторное решение отправляет снова;
- `POST /auth/check-phone { phone }` → `{ exists }` — подсказка до кода, не право входа; `429`/`503` — «не знаем», вход
  не блокируем (`useCheckPhone`);
- вход через Google — только сотрудникам магазинов (владелец, администратор филиала, кассир), регистрации через Google
  нет: сначала вход по номеру, потом «Привязать Google» в профиле (`POST/DELETE /auth/me/google`, состояние — `google`
  в `/auth/me/profile`), дальше `POST /auth/google { idToken, deviceId }`. Клиенты и агентство — без Google.
  Кнопку рисует Google Identity Services (`GoogleSignIn`, `GoogleLink` в `@loal/app-kit`), Web client ID —
  `VITE_GOOGLE_CLIENT_ID` при сборке (`GOOGLE_CLIENT_ID` в compose); пусто или `503 GOOGLE_SIGN_IN_DISABLED` — кнопки нет;
- филиалы: `PATCH` — переименовать, `DELETE` — закрыть (`archivedAt`, операции его помнят; `?includeArchived=true`),
  пока в филиале люди — `409 BRANCH_HAS_MEMBERS`. Закрывает и переименовывает только владелец;
- интеграция с OctōPAY (`docs/Rabotka.md`, `docs/API.md`): владелец выбирает в OctōPAY счёт в KGS, получает
  одноразовый код `loal_link_…` и вводит его в «Обзоре» (`…/octopay-integration`: GET — все, POST/DELETE — владелец).
  Код — секретное поле, нигде не храним. Счёт выставлять можно только при `ready` (`isOctopayIntegrationReady`;
  старый ответ без полей готовности — «не готово»); причина — `invoiceNotReadyReason` строкой, подсказки по ней;
- тариф магазина (`tariff`: `octopay` | `loal`, `tariffOf`, `TARIFF_LABELS`) не выбирают — он следует из связи с
  OctōPAY: связь подключена и включена → «OctōPAY + Loal» (Loal бесплатен, бонусы принимаются без оплаченной
  подписки, есть «Счёт клиенту»), иначе «Только Loal» (помесячная подписка, бонусы — касса). Приходит у магазина,
  подписки (`isActive` = оплачено или пакет, `paidActive` — только оплачено, `expiresAt: null` у пакета без оплаты),
  в каталоге и обзоре кассира. «Счёт клиенту» в меню только на пакете. Подписка `404` — «ещё не оплачивали», не ошибка.
  Бэкенд сам сверяет связь раз в 10 минут, так что тариф меняется и без визита владельца. Пока цена «Только Loal» — 0,
  подписка не нужна вовсе: счёт отвечает `409 MERCHANT_ACCESS_FREE` (показываем «доступ бесплатный»), у кассира в
  подписке `free: true` — «Бесплатно». Регистрация на лендинге бесплатна на всех моделях;
- счёт клиенту — `POST …/client-payments { requestId, amount }`: телефона нет, его вводит плательщик на странице
  OctōPAY и сам выбирает бонусы (банк / бонусы / бонусы + банк). `requestId` — UUID попытки: тот же при повторе
  после ошибки или таймаута, новый только после успеха (`OCTOPAY_NOT_READY`, `OCTOPAY_INVOICE_LIMIT_REACHED`,
  `IDEMPOTENCY_CONFLICT`, `502` — понятным текстом). Выставляют все три роли; форма и список общие —
  `ClientPaymentForm`/`ClientPaymentList` в `@loal/app-kit`. В UI пишем «OctōPAY»;
- самостоятельная оплата по NFC/QR (`docs/octopay.md`): экраны покупателя живут в OctōPAY, в Loal — только кассы
  (`…/checkout-points`, владелец, тариф OctōPAY; название, филиал и проценты фиксируются при создании, только отключить)
  и список «Счёт клиенту»: `source: self_service`, касса, номер OctōPAY, разбивка `bonusAmount`/`bankAmount` (`null` —
  «ещё не подтверждена», не ноль), оплачен — `paid` + `fulfilled` (`clientPaymentOutcome`), список перечитывается раз в 5 с;
- название товара при списании необязательно: пусто или нет поля — «Покупка» (у 1С по-прежнему обязательно);
- цены тарифов магазинов — экран «Тарифы» (`/admin/v1/tariffs`: `loal`, `loal_octopay`, целые сомы, 0 — бесплатно);
  `merchantAccessPriceKgs` в настройках платформы устарел. Цена подписки клиента — в настройках (`cardSubscriptionPriceKgs`),
  счёт считает сервер: магазину шлём только `{ months }`, сумму показываем из ответа. Цена 990 на
  лендинге и в кабинете клиента — только для показа, держать равной цене в админке;
- самозаписи с программой в адресе больше нет: только `/v1/public/enroll`; старые QR
  `/enroll/:templateId/:programId` клиентский кабинет переводит на `/enroll`;
- рефералы (REF-01, `docs/referrals/`): сервер раздаёт ссылки `loal.kg/ref/{code}`, лендинг редиректит их
  в кабинет клиента `/ref/{code}` — там `POST /v1/public/referrals/{code}/visit { deviceId }` (404 — нет кода,
  409 — своя ссылка), код живёт на устройстве 30 дней, регистрация — `/auth/register` с `referralCode` и тем
  же `deviceId`. Раздел «Друзья»: `GET /v1/me/referrals` (404 — не подключён), `POST /v1/me/referrals/enroll`
  (карта + 2 000 один раз); приглашённые обезличены. В истории — `kind: "referral"`;
- кабинет кассира `apps/cashier` (cashier.loal.kg) — для `staff`: «Обзор» (`/v1/cashier/overview`, `branch` может
  быть `null`, `subscription: null` — подписки нет), «Списать бонусы» (`POST /v1/redemptions`, потолок — свой
  `coverage-limit`), «Счёт клиенту», «История» (`/v1/cashier/redemptions`: только `customerName`, `amount`,
  `createdAt`), «Витрина» и «Касса» на просмотр. Касса (`RedeemForm`, `QrScanButton`) общая — в `@loal/app-kit`.
  В журнале списаний колонка «Кассир» из `cashierName` (`null` у 1С и старых — «—»);
- ручки `/v1/scan/*`, `/v1/cards/{serial}/scan-confirm*`, `/v1/pos-settings` помечены как наследие,
  новый код на них не завязываем.

## Данные и формы

- Любой ответ API разбирается схемой Zod из `@loal/api`: схемы описаны как `looseObject`, лишние
  поля бэкенда не ломают экран, отсутствующие — ломают сразу и явно.
- Формы — Formik плюс `zodValidate` из `@loal/forms`: одна схема и проверяет поле, и описывает тело
  запроса. Ошибку поля показываем после `touched`, ошибку отправки кладём в `status` формы.
- В `catch` формы вызываем `applyServerIssues(error, helpers, «человеческий текст»)`: ошибки полей из
  ответа (`issues`) ложатся на свои поля, остальное — в `status`. Прятать их в одну строку внизу
  нельзя: человек должен видеть, что именно поправить.
- Внутрь каждой формы ставим `<FocusFirstError form={form} />` — после неудачной отправки фокус
  переходит на первое поле с ошибкой.
- Телефон — только через `PhoneInput` из `@loal/ui/inputs` и `phoneSchema` / `optionalPhoneSchema` из
  `@loal/api`. Обе стороны на `libphonenumber-js`, как и бэкенд: выбор страны (по умолчанию KG), формат
  на лету по правилам страны, проверка существования номера. Значение — код страны и цифры без `+`
  (`996700123456`, `77011234567`), так его хранит и сравнивает сервер. Номер без кода (`0700…`)
  считаем кыргызским; несуществующий отклоняем, а не «чиним» до чужого. Пустой телефон не шлём.
- Телефон аккаунта — в `GET /auth/me/profile` (`phone`). Номер входа, запомненный на устройстве
  (`shared/lib/remembered-phone`), — только запасной путь для старого шлюза; при выходе стирается.
- Права проверяет сервер. `RequireAuth` и проверки ролей на фронте — удобство интерфейса, а не
  защита: не полагаться на них при показе чувствительных данных.
- Токены — пара в localStorage: access (12 ч, единственный Bearer) и refresh (30 дн, ключ `<ключ>.refresh`),
  ключ свой у каждого кабинета. Обычный `401` клиент `@loal/api` сам лечит: один общий `POST /auth/refresh`
  на все параллельные запросы, сохранить новую пару, один повтор. Выход — только при
  `INVALID_REFRESH_TOKEN`, `SESSION_REPLACED` или без refresh-токена. Вход, регистрация и смена профиля
  отдают пару — сохраняем обе (`signIn(tokens)`). «Выйти» шлёт `POST /auth/logout` (гасит сессию на
  сервере) и стирает токены сразу, ответа не ждёт.
- Ветвимся по стабильному коду ошибки (`ApiError.code`: `SESSION_REPLACED`, `CARD_FROZEN`,
  `SUBSCRIPTION_OFFER_CHANGED`, `OTP_*`, `PROMO_*`, `CARD_REQUIRED`, `MERCHANT_SLUG_TAKEN`,
  `CUSTOMER_PHONE_TAKEN`, `EMAIL_TAKEN`, `COVERAGE_LIMIT_LOCKED` + `nextChangeAt`, `INSUFFICIENT_POINTS`),
  а не по русскому `message`. `OTP_RATE_LIMITED` несёт `retryAfter` (`ApiError.retryAfter`).

## Интерфейс кабинетов

- Набор компонентов кабинетов ровно один — `@loal/ui/shadcn`. Двух параллельных наборов быть не
  должно: именно из-за этого часть экранов однажды осталась в старом виде.
- Компоненты в духе shadcn живут в `@loal/ui/shadcn` (Button, Card, Input, Table, Dialog, Tabs,
  Badge, состояния загрузки и ошибки). Они собраны на Radix и CVA, но раскрашены нашими токенами:
  `bg-primary` — это флеймовый Loal, а не серый по умолчанию. Новый общий элемент добавляем туда же.
- Каркас `AppShell` (`@loal/ui/app-shell`): на десктопе разделы слева, на телефоне узкая шапка и
  выезжающее меню. Таблица `Table` на телефоне превращает строки в карточки — у ячеек `label="…"`
  (подпись) и `primary` (главная ячейка); `stack={false}` оставляет прокрутку вбок.
- Иконки — HugeIcons через `<Icon icon={...} />` из того же пакета: размер по строке текста, цвет
  наследуется, из чтения скрыты.
- Токены в `theme.css` продублированы привычными для shadcn именами (`--background`, `--foreground`,
  `--primary`, `--muted-foreground`, `--border`, `--radius`), поэтому компоненты из документации
  shadcn встают без перекраски.

## Бренд и тексты

Источник — `docs/Loal брендбук-3.pdf` и `docs/LOAL_content_plan_product_focused.docx`.

- Палитра (`packages/ui/src/theme.css`): акцент `#FF5D34`, светлый оранжевый `#FFA33B`, градиент
  `#FF4A3E → #FFCC91`, фон `#FCF9F9`, графит `#161515`. Имена токенов прежние (`flame`, `amber`,
  `graphite`…), меняются значения. Шрифты: Nunito Sans — заголовки, Nunito — текст (с cyrillic-ext
  для кыргызского).
- На оранжевых кнопках текст белый (решение владельца продукта) и жирный — у белого на `#FF5D34`
  контраст 3:1. На светлом конце градиента белый не читается вовсе — там графит.
- Два направления: Loal (покупатели, дескриптор «Бонусы по подписке») и Loal Corporate (бизнес,
  тёмная подача, `<Logo direction="corporate" />`). Кабинет партнёра — Corporate.
- Пишем «Loal», не «LOAL». Никогда «15 000 сом бонусами»: это читают как деньги. Правильно —
  «15 000 бонусов», и отдельно: 1 бонус = 1 сом только в бонусной части покупки, вывести нельзя,
  процент задаёт партнёр, остаток в новый период не переносится. Выгоду не обещаем всем.
- Бизнесу не пишем «сделаем вам карту» — это прежняя подача.

## Общее

- Приложения не импортируют код друг друга; общее — только через `packages/`.
- Бренд (цвета, шрифты, логотип, поля форм) — в `@loal/ui`, а не копиями в приложениях.
- Ссылки между доменами — через константы (`SITE_URL`, `API_URL`, `PARTNER_APP_URL`,
  `CLIENT_APP_URL`, `CASHIER_APP_URL`), не хардкодом.
- Деплой — Docker Compose плюс Traefik бэкенда; фронтенд не кладётся внутрь папки бэкенда, её
  деплой стирает содержимое целиком.
