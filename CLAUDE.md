# Loal — правила архитектуры

Монорепо pnpm: `apps/landing` (loal.kg), `apps/admin` (admin.loal.kg), `apps/partner`
(partner.loal.kg), `apps/client` (client.loal.kg). Общее — в `packages/`. Подробности и команды —
README.md. Бэкенд живёт в соседнем репозитории `cashup_platform`, шлюз — `loal.promconsult.pro`.

## Лендинг — SEO прежде всего

Страницы статические (SSG) или серверные; текст должен попадать в HTML без JavaScript.
`"use client"` — только для интерактивных островков (анимации, калькулятор, карта, формы).
У каждой новой страницы — `metadata` с title, description, canonical и Open Graph, и строка в
`app/sitemap.ts`. Сборка должна показывать страницы как `○ (Static)`.

## Кабинеты — чистый CSR и FSD

Vite SPA, без SSR, закрыты от индексации (`noindex` в index.html, robots.txt, заголовок в
`infra/nginx/spa.conf`). В sitemap лендинга их не добавлять.

Слои Feature-Sliced Design, импорт разрешён только вниз:

```
app → pages → widgets → features → entities → shared
```

- слой не импортирует сам себя через соседний срез: общее поднимается на слой ниже или в пакет;
- запросы к API живут в `entities/<домен>/api.ts` рядом с ключами кэша, экраны их только вызывают;
- действия пользователя (вход, смена статуса, добавление сотрудника) — `features/`, а не в странице;
- новый общий для кабинетов кусок — сразу в `packages/` (`@loal/ui`, `@loal/app-kit`), не копией.

## Контракт с бэкендом

`docs/API.md` — справочник шлюза, его обновляют в том же коммите, что и само API. Это источник
правды: схемы в `@loal/api` следуют ему, а не тому, что удалось вычитать в коде бэкенда. Если экран
падает на разборе ответа, сначала сверяемся с этим файлом.

Модель после 23 сентября 2026: **карта, клиент, шаблон и программа принадлежат платформе**,
а заведение (`merchant`, бывший `store`) владеет только своими сотрудниками, подпиской, журналом
списаний, витриной и обменом с 1С.

Что из него важно помнить:

- платформенные адреса без заведения в пути (`/admin/v1/customers`, `/admin/v1/cards`,
  `/admin/v1/templates`, `/admin/v1/loyalty-programs`) открыты только агентству — заведению `403`;
- всё про заведение живёт под `/admin/v1/merchants/{merchantId}/...`;
- в токене членства лежат в `merchants[]`, внутри — `merchantId`; старые токены не подойдут;
- у держателя карты есть свой кабинет: `/v1/me/card` и `/v1/me/history` читают человека из
  токена, идентификатора в адресе нет; `404` на карте значит «ещё не выпускали», а не ошибку;
- подписка принадлежит человеку, а не карте: повторный `POST` продлевает её, добавляя месяцы,
  а баллы за них выдаются в начале каждого периода, не сразу;
- витрину (`profile`) PUT заменяет целиком: шлём все шесть полей, пустое — как `null`,
  фотографии — как `[]`; картинки грузятся отдельным запросом до сохранения;

- вход отправляет `deviceId` — постоянный, создаётся один раз и живёт в localStorage; у аккаунта
  одна активная сессия;
- если аккаунт открыли на другом устройстве, закрытые запросы отвечают `401` с
  `error: "SESSION_REPLACED"`. Такой ответ нельзя повторять и нельзя молча обновлять сессию:
  чистим токен и показываем сообщение на входе (`ApiError.isSessionReplaced`);
- регистрация сразу выдаёт токен, отдельный вход после неё не нужен; без кода приглашения
  получается сотрудник без доступа к кабинету, с кодом — владелец магазина;
- вход возможен и по телефону с кодом из WhatsApp: код живёт 5 минут, на него даётся 5 попыток,
  повтор не чаще раза в минуту (429 с текстом, сколько ждать); код одноразовый — успешный вход или
  регистрация его поглощают;
- у магазина подписка (`isActive`) отвечает за приём бонусов, счета — только за оплату;
- ошибки проверки приходят с массивом `issues` (путь до поля и текст) — он лежит в `ApiError.issues`;
- живые поля карты — по `key` (`balance`, `cardNumber`, `memberName`, `phone`, `memberSince`, `punch`,
  `tier`, `tierReward`, `discount`, `bonusItem`): их `value` сервер подменяет сам. Синтаксиса `{{…}}`
  нет. `dateStyle`/`timeStyle` — только у дат, иначе Apple отвергает карту целиком;
- правка шаблона (`PUT /admin/v1/templates/{id}`) сразу уходит на все выданные карты push-ом,
  отката нет: в редакторе сохранение опубликованной карты идёт только через подтверждение с числом
  держателей; тело — весь `design`, пустые необязательные поля выкидываем (`cleanDesign`);
- потолок процента (`coverage-limit`) заведение меняет раз в месяц (`409` до `nextChangeAt`),
  агентство — когда угодно; касса берёт меньшее из 30% и потолка. Форма общая — `@loal/app-kit`;
- `POST /v1/redemptions` шлёт `merchantId`, только если человек работает в нескольких заведениях:
  с одним местом работы сервер лишнее поле отклоняет;
- пустые необязательные поля уходят на сервер как `null`, а не `""` — строку сервер не пропустит
  (почта заведения, проценты уровня);
- ручки `/v1/scan/*`, `/v1/cards/{serial}/scan-confirm*`, `/v1/pos-settings` помечены как наследие,
  новый код на них не завязываем.

## Данные и формы

- Любой ответ API разбирается схемой Zod из `@loal/api`: схемы описаны как `looseObject`, лишние
  поля бэкенда не ломают экран, отсутствующие — ломают сразу и явно.
- Формы — Formik плюс `zodValidate` из `@loal/forms`: одна схема и проверяет поле, и описывает тело
  запроса. Ошибку поля показываем после `touched`, ошибку отправки кладём в `status` формы.
- В `catch` формы вызываем `applyServerIssues(error, helpers, «человеческий текст»)`: ошибки полей из
  ответа (`issues`) ложатся на свои поля, остальное — в `status`. Прятать их в одну строку внизу
  нельзя: человек должен видеть, что именно поправить.
- Внутрь каждой формы ставим `<FocusFirstError form={form} />` — после неудачной отправки фокус
  переходит на первое поле с ошибкой.
- Телефон приводится к виду `996XXXXXXXXX` схемой `phoneSchema`: принимаем `700…`, `0700…`, `+996 …`.
  Если цифр не девять, номер отклоняется, а не «чинится» до чужого.
- Права проверяет сервер. `RequireAuth` и проверки ролей на фронте — удобство интерфейса, а не
  защита: не полагаться на них при показе чувствительных данных.
- Токен хранится в localStorage (у бэкенда нет refresh и httpOnly-cookie), ключ свой у каждого
  кабинета. На 401 кабинет разлогинивается — это единственная стратегия обновления сессии.

## Интерфейс кабинетов

- Набор компонентов кабинетов ровно один — `@loal/ui/shadcn`. Двух параллельных наборов быть не
  должно: именно из-за этого часть экранов однажды осталась в старом виде.
- Компоненты в духе shadcn живут в `@loal/ui/shadcn` (Button, Card, Input, Table, Dialog, Tabs,
  Badge, состояния загрузки и ошибки). Они собраны на Radix и CVA, но раскрашены нашими токенами:
  `bg-primary` — это флеймовый Loal, а не серый по умолчанию. Новый общий элемент добавляем туда же.
- Иконки — HugeIcons через `<Icon icon={...} />` из того же пакета: размер по строке текста, цвет
  наследуется, из чтения скрыты.
- Токены в `theme.css` продублированы привычными для shadcn именами (`--background`, `--foreground`,
  `--primary`, `--muted-foreground`, `--border`, `--radius`), поэтому компоненты из документации
  shadcn встают без перекраски.

## Бренд и тексты

Источник — `docs/Loal брендбук-3.pdf` и `docs/LOAL_content_plan_product_focused.docx`.

- Палитра (`packages/ui/src/theme.css`): акцент `#FF5D34`, светлый оранжевый `#FFA33B`, градиент
  `#FF4A3E → #FFCC91`, фон `#FCF9F9`, графит `#161515`. Имена токенов прежние (`flame`, `amber`,
  `graphite`…), меняются значения. Шрифты: Nunito Sans — заголовки, Nunito — текст (с cyrillic-ext
  для кыргызского).
- На оранжевых кнопках текст белый (решение владельца продукта) и жирный — у белого на `#FF5D34`
  контраст 3:1. На светлом конце градиента белый не читается вовсе — там графит.
- Два направления: Loal (покупатели, дескриптор «Бонусы по подписке») и Loal Corporate (бизнес,
  тёмная подача, `<Logo direction="corporate" />`). Кабинет партнёра — Corporate.
- Пишем «Loal», не «LOAL». Никогда «100 000 сом бонусами»: это читают как деньги. Правильно —
  «100 000 бонусов», и отдельно: 1 бонус = 1 сом только в бонусной части покупки, вывести нельзя,
  процент задаёт партнёр, остаток в новый период не переносится. Выгоду не обещаем всем.
- Бизнесу не пишем «сделаем вам карту» — это прежняя подача.

## Общее

- Приложения не импортируют код друг друга; общее — только через `packages/`.
- Бренд (цвета, шрифты, логотип, поля форм) — в `@loal/ui`, а не копиями в приложениях.
- Ссылки между доменами — через константы (`SITE_URL`, `API_URL`, `PARTNER_APP_URL`,
  `CLIENT_APP_URL`), не хардкодом.
- Деплой — Docker Compose плюс Traefik бэкенда; фронтенд не кладётся внутрь папки бэкенда, её
  деплой стирает содержимое целиком.
